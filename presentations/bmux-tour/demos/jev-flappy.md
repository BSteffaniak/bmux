# Jev Flappy Bird finale

A standalone Python 3 terminal application launched by the tour's normal
`playbook-demo`. Jev-specific behavior stays in the application, not BMUX core,
presenter components, or plugin API contracts.

## Run it

Set **only `JEV_API_KEY`** privately in the environment before starting your
presentation runtime. Launch the tour as usual using the approved executable
and matching plugins described in [the tour README](../README.md). Explicitly
start the demo on the final slide. No application-path, socket, model, backend,
or `BMUX_PLAYBOOK_APP_ENV_` variables are required.

The demo calls the official TypeSafe API directly at
`https://api.typesafe.ai/v1/systemone`, model `jev-1.13.0`. Set **only
`JEV_API_KEY`**, using a key issued by the TypeSafe console (not a gateway key).
Python 3 with curses must be on the runtime's PATH; no pip packages are needed.
The key must be in the **playbook owner's launch environment**; exporting it
after an existing owner started cannot change that process. Prefer a fresh,
separately owned presenter runtime rather than a shared server.

`JEV_MODEL` is an optional pinned-model override. There is no gateway/backend
selection or credential fallback. Legacy `JEV_BACKEND`, `JEV_BASE_URL`, and
`TYPESAFE_API_KEY` settings are ignored and are not forwarded by the playbook.
Production always uses verified HTTPS to the direct API; only offline tests
can construct a loopback HTTP client. Redirects and upstream diagnostic bodies
are never displayed.

Opening the presentation or the slide alone does not execute the demo. If the
key is missing when execution starts, the app reports a missing credential and
exits; the playbook startup check fails. No missing-key request is sent.

## Declared inputs and isolation

The playbook declares:

```text
@resource FLAPPY_APP=jev_flappy.py
@env-from JEV_API_KEY JEV_MODEL
@env-mode clean
```

`FLAPPY_APP` is internal wiring generated by playbook file resolution. You do
not set it. Relative resource paths resolve against the declaring script, are
included in the bounded no-symlink approval closure, and are frozen into the
attempt's private source directory. Changing the game invalidates prior closure
approval just like changing the DSL or an include. The Python interpreter itself
is an external runtime dependency and is not authenticated by that closure.

`@env-from` names are approved script inputs; their values are read only at
execution and kept out of the parsed model, preparation JSON, source snapshots,
and status records. Managed workers still clear the general host environment;
only declared names are forwarded, never the compatibility probe. The clean
sandbox receives those selected values, application resource paths, literal
playbook environment, and its normal deterministic runtime defaults. This is
not a secret store or protection against the approved application itself:
its processes can read the imported inputs. Never share an owner with untrusted
applications or put keys in `@env`, scripts, slide content, or command text.

## Lifecycle and controls

Jev uses an explicit `choice` judgement with stable `FLAP` and `WAIT` IDs.
The selected ID is executed directly: confidence and probabilities are displayed
and validated, never converted into a flap threshold. Each observation includes
safe gap edges, contact/clear times, ceiling/floor clearance, and exact
forecasts
for both actions using the same physics as the game. Five ticks are committed;
10/15-tick coasting samples illustrate momentum only, not a mandatory action
horizon. Forecasting never changes live state or chooses an action. The prompt
prioritizes immediate survival and tick-5 alignment, not the distant coasting
endpoint. No recommendation or safety pilot overrides Jev's choice.

Jev chooses flap/wait for five simulation ticks at a time. The target period is
five ticks at 30 Hz (166.7 ms). Request latency counts **inside** that period:
ticks run as their deadlines arrive, or catch up immediately when a slower
response arrives. The step takes `max(request latency, 166.7 ms)` plus bounded
local polling/work, not latency plus a fresh animation period. Physics never
advances speculatively while waiting. Rendering stays capped at 30 Hz; the
transport is polled every 2 ms. Slow responses can still look stepped—this is
latency-adaptive gameplay, not a claim of real-time original Flappy Bird timing.
There is no hidden pilot. Game-over automatically starts another attempt.
Failed requests freeze physics and retry with bounded backoff. There is no
overall lifetime/request/spend cap; provider usage continues while active.

One spawned worker owns one reusable verified HTTPS connection, with at most
one request in flight and no queue. Successful decisions reuse both worker and
connection when the server permits keep-alive. Errors discard the connection;
there is no transparent POST replay. Pause, restart, stop, or a 15-second total
deadline terminate and reap the worker and close its socket before replacement.
Responses and IPC messages are size-bounded. Cancellation cannot undo remote
billing. Redirects, unverified TLS, and ambient proxy configuration are not
used.

Status/decision traces report dispatch (including first worker spawn),
connection
setup (DNS/TCP/TLS together), request-to-headers, body/decode, transport total,
and end-to-end time including polling. Setup is zero on reused connections.
These are local measurements: headers time includes network and server work,
not an invented server-inference-only duration. The display shows the dominant
components; private `status` and `trace` expose the full breakdown without keys.

## Fixed widescreen demo gameplay

The demo uses the classic
[FlapPyBird reference, pinned commit](https://github.com/sourabhv/FlapPyBird/blob/b7cc55bdd82e2c940d9a24fb910bf3415753ee11/flappy.py)
for 30 Hz gravity (1 px/tick²), flap velocity (−9 px/tick), maximum descent
(10 px/tick), pipe width (52 px), spacing (144 px), horizontal speed (128 px/s),
and the approximate 34×24 px bird collision box. A flap skips gravity that
tick;
the top is not lethal and flapping is disabled above the top boundary.

This is deliberately an easier widescreen demo, not a faithful difficulty clone:

- The playfield fills the available terminal width and height below the HUD.
  At 100×30 this is 97×22 cells, not a narrow portrait strip.
- The horizontal world is expanded to match that widescreen camera, assuming
  cells twice as tall as wide. Pipes remain about 5–6 columns wide and the bird
  about 3–4 columns, rather than stretching them to fill the extra space.
- The actual pipe opening is **160 reference pixels**, up from 100: about
  **nine rows** at the default viewport instead of five/six. Collision-safe
  bird-center clearance increases from 76 to 136 reference pixels. Rendering,
  collisions, forecasts, and the agent's safe interval all use this same gap.
- Gap centers are seeded random values with 40px minimum top/bottom pipe
  segments. The first pipe starts at 60% of the world width; following pipes
  keep the fixed spacing through and beyond the right edge. New pipes are
  generated offscreen, never recycled into the middle of the playfield.
  Difficulty never ramps with score or attempt.

Art and collisions share world geometry, rounded to terminal cells (the bird
uses at least one row). Resizing fills the new viewport without changing the
physics. Different terminal aspect ratios and coarse cell rounding remain
visual approximations. Pipe overlap remains about 0.67 simulation seconds;
provider latency above 166.7ms can still stretch wall-clock time.

The reference is an open-source recreation, not verification of the proprietary
original binary. Rectangular collision (no sprite hit masks/rotation), seeded
randomness, center-based scoring, and five-tick agent decisions are explicit
demo approximations. Offline tests cover full-width rendering, widened collision
clearance, exact forecasts, lifecycle, and a constant-gap multi-pipe
fixture—not
Jev's live score or survival on arbitrary random courses.

After successful startup, the existing managed runner retains the actual sandbox
past the playbook startup timeout. Presenter **Stop**, **Restart**, closing the
presenter, and explicit `on_leave: stop` own cleanup. No sleep loop or invented
presentation execution mode is involved. Standalone `playbook run` is not the
retained presenter mode: it cleans up after its steps.

The game creates its control socket automatically in the owned sandbox runtime
and a private `.jev-flappy-control.json` locator in the sandbox HOME. No public
socket or checkout file is created. Runtime teardown removes these paths even
if the game is forcibly terminated. Each managed attempt has separate paths.

Presenter Pause/Step controls the **script**, not the application. Optional game
controls can be sent from a private terminal, using the locator inside the
specific attempt's sandbox HOME (do not share this private path publicly):

```bash
python3 presentations/bmux-tour/demos/jev_flappy.py \
  --control-file /private/attempt/sandbox/.jev-flappy-control.json --control pause
```

Other actions are `resume`, `restart`, `status`, `trace`, and `stop`. `trace`
returns the newest four retained events with explicit completeness metadata;
the in-memory ring holds at most 32 events. Decision events contain the exact
credential-free observation, normalized choice/probabilities/confidence, and
executed action. Collision events identify ceiling, floor, or pipe. No HTTP
headers, credential configuration, or upstream diagnostic bodies are retained.
Round restart keeps
the best score and discards outstanding decisions. Re-entering the slide is
inert until explicit presenter Play/Restart.

For standalone rehearsal, run `python3
presentations/bmux-tour/demos/jev_flappy.py`
with the key set. Keys: `p` pause/resume, `r` restart, `q` quit. A private
temporary
socket and locator in HOME are generated automatically; the optional
`--control-file` flag selects a different locator. Embedded presenter surfaces
are not assumed to forward keyboard input to applications.

## Validation

Run inside the repository's Nix development shell:

```bash
python3 -m unittest discover -s presentations/bmux-tour/demos -p 'test_jev_flappy.py' -v
python3 presentations/bmux-tour/demos/smoke_jev_flappy.py \
  --binary /absolute/path/to/bmux --plugins /absolute/path/to/matching/plugins
```

The smoke uses fake loopback credentials and isolated short `/tmp` paths. It
checks frozen application startup, generated controls, retention past the
startup
deadline, pause/restart, auto-retry, slide-leave cleanup, re-entry/restart, and
presenter-exit cleanup during a request. Terminal evidence is bounded and
private.
It does not prove real-provider playing ability, latency, cost, or
browser/Canvas
acceptance. Rehearse those separately with the intended audience setup and key.
